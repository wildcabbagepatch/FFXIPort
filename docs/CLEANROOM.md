## What was read in the provided client, and how it was used

All 14 provided files were read in Phase C. Several of them contain
**traces of the former wire format** in comments and code: the command
strings, record kinds and verb names in `FFXIPort.lua`, `travel.lua`,
`echo.lua` and `model.lua`, and references to the server contract in
`travel.lua`. This was expected; the owner allowed these integration modules
to be inspected and adapted. They were used only to learn which functions
the UI calls and what the user sees. None of that wording informed FPX/1,
which was already frozen. Every old-format string in the adapted modules was
removed or replaced.

## Boundary notes (stated rather than hidden)

1. **Catalogue generator input.** The header of `catalog_data.lua` lists
   `server/modules/custom/late/ffxiport.lua` (the previous server module)
   among the generator's inputs. The catalogue is the "existing game catalog"
   the task explicitly allows. It was used unchanged, and only for ids, zones,
   groups and unlock bits. Each of those values was independently matched
   against upstream LandSandBoat by `tools/verify_catalog_vs_lsb.lua` (193/193
   rows). The `city` table in the catalogue (a city-group extension) was **not**
   used by the new server. Client pricing now comes only from server offers.
2. **Payment-method set.** FPX/1 has a generic offer model. The concrete server
   policy (hp/sg/sp: gil or CP, rp: gil or IS) was taken from the existing UI's
   payment selector (`travel.lua` `METHODS`, `config.lua` `pay_method*`), so
   the user-facing behaviour stays the same. CP amounts and the gil price for
   portals/crystals are new policy defaults, not recovered values.
3. **Model knowledge.** The implementer is a language model. Its general
   training knowledge of public LandSandBoat code and of FFXI is not a
   controllable input. No Driftwood/dwport or previous-FFXIPort material was
   knowingly recalled or used, but this cannot be proven for model knowledge.
4. **Phoenix vs upstream.** The authoritative Phoenix tree was not available.
   Upstream LandSandBoat was used instead (owner's choice), so Phoenix-specific
   API differences remain unverified.
